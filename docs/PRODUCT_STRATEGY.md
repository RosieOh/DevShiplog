# Devshiplog 제품 전략

## 1. 문제

기술 글은 **시간이 지나면 틀린 글이 된다.** 그런데 아무도 그걸 관리하지 않는다.

개발자라면 다 겪는 일이다.

> 검색해서 나온 글을 따라 했는데 안 된다.
> 스크롤을 올려 날짜를 본다. 2023년.
> 어느 버전 기준인지는 안 적혀 있다.
> 댓글에 "저도 안 돼요" 가 세 개 달려 있고 답이 없다.

**읽는 쪽**은 그 글을 믿어도 되는지 판단할 방법이 없다.
**쓰는 쪽**은 자기 글이 낡았다는 걸 모른다. 알아도 어느 글부터 고쳐야 할지 모른다.

기존 블로그 플랫폼(Velog, Medium, Tistory, 노션)은 이 문제에 대해 **구조가 없다.**
날짜 한 줄이 전부다. 날짜는 "언제 썼는가" 지 "지금도 맞는가" 가 아니다.

## 2. 우리가 다르게 하는 것

**낡음(staleness)을 1급 개념으로 다룬다.**

글은 텍스트 덩어리가 아니라 **"어떤 기술 스택의 어떤 버전에서, 언제 확인된 절차"** 다.
그렇게 다루면 할 수 있는 일이 생긴다.

| | 기존 플랫폼 | Devshiplog |
|---|---|---|
| 글의 전제 | 안 적혀 있음 | `React 18.3 · Node 20 · TypeScript 5.4` 로 구조화 |
| 신뢰도 | 작성 날짜 한 줄 | 마지막 **검증** 시각 + 스택 최신성 |
| 낡은 글 | 방치 | 독자에게 경고, 작성자에게 갱신 목록 |
| "안 돼요" | 댓글에 묻힘 | 구조화된 신호 → 작성자 대시보드 |
| 탐색 | 태그 (자유 문자열) | 스택+버전 (정규화) |

### 왜 이게 방어 가능한가

- **Velog 가 따라 하기 어렵다.** AI 버튼은 하루면 붙이지만, 이건 데이터 모델부터 다르다.
  기존 글 수백만 건에 스택 메타데이터가 없다.
- **데이터가 쌓일수록 강해진다.** "React 18 글 중 최근 6개월 안에 검증된 것" 같은 질의는
  우리만 할 수 있고, 글이 쌓일수록 가치가 커진다.
- **AI 자산과 맞물린다.** 이미 초안을 생성하므로, 스택 추출·갱신 제안도 같은 파이프라인에 얹는다.

## 3. 누가 돈을 내는가

개인 개발자 블로그는 수익화가 어렵다. Velog 도 못 했다.
**돈은 회사 기술 블로그에 있다.**

회사가 기술 블로그를 운영하는 이유는 하나다 — **채용 브랜딩.**
그리고 대부분 실패한다.

- 개발자가 글을 안 쓴다 (시간 없음, 뭘 쓸지 모름)
- 리뷰가 안 돈다 (누가 봐야 하는지 불명확)
- 발행 후 방치된다 (낡은 글이 회사 기술 수준을 오해하게 만든다)
- 효과를 못 잰다

우리가 이미 가진 것(AI 초안, 문체 학습, 민감정보 검수)과 지금 만드는 것(신선도 관리)이
정확히 이 네 가지를 친다.

| 단계 | 제품 |
|---|---|
| **개인 (무료)** | 블로그 호스팅, AI 초안, 신선도 관리 |
| **팀 (유료)** | 조직 워크스페이스, 리뷰 워크플로, 발행 승인, 갱신 담당자 지정 |
| **기업** | 자체 도메인, SSO, 채용 페이지 연동, 유입 분석 |

개인 무료는 비용이 아니라 **유통 채널**이다. 개발자가 개인 블로그를 여기 쓰면,
회사 블로그를 옮길 때 우리를 떠올린다.

## 4. 지금 만드는 것 (이번 단계)

신선도 관리의 최소 완결 형태. 개인 사용자 기준으로 먼저 돌린다.

1. **스택 메타데이터** — 본문에서 자동 추출하고 작성자가 보정. `react@18.3` 형태로 정규화
2. **검증 시각** — "지금도 동작함" 을 작성자가 찍는다. 날짜와 다른 개념이다
3. **신선도 계산** — 검증 경과 + 스택 최신성으로 `fresh / aging / stale`
4. **독자 신호** — "지금도 되나요?" 를 구조화해서 받는다. 댓글보다 가볍다
5. **스택 탐색** — `/stacks/react` 에서 버전별로, 신선한 것 우선
6. **작성자 대시보드** — 갱신이 필요한 내 글 목록

## 5. 하지 않기로 한 것

- **코드 자동 실행 검증.** 매력적이지만 샌드박스 인프라가 제품보다 커진다.
  작성자의 자기 신고 + 독자 신호로 시작한다. 신뢰는 사람이 만들고 우리는 구조만 준다.
- **스택 최신 버전 자동 수집.** 외부 레지스트리 크롤링은 의존성이 크다.
  우선 우리가 관리하는 목록으로 시작하고, 수요가 확인되면 자동화한다.
- **개인 블로그 유료화.** 유통 채널을 막는 짓이다.

## 6. 성공을 어떻게 아는가

이번 단계에서 볼 것:

- 발행 시 스택을 **보정하는 비율** — 자동 추출이 쓸 만한가
- 검증 버튼을 **다시 누르는 비율** — 갱신 루프가 도는가
- 독자 신호가 **작성자를 움직이는가** — 신호 받은 글의 갱신율

이 셋이 안 돌면 신선도는 우리만 좋아하는 기능이다. 그때는 접는다.
