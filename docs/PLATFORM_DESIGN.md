# 블로그 플랫폼 설계

Devshiplog 는 "남의 블로그에 쓸 초안을 만들어주는 도구" 에서
**"글을 쓰고 발행하고 읽는 플랫폼"** 으로 범위가 확장되었습니다.
이 문서는 그 과정에서 내린 결정과 이유를 남깁니다.

## 1. Draft 와 Post 를 분리한다

```
Draft (비공개 작업본)  ──발행──▶  Post (공개 스냅샷)
  · 2초마다 자동저장                 · slug, published_at
  · 버전 스냅샷                      · 캐시 대상, 공개 URL
  · AI 생성/변형 대상                · 태그, 시리즈
```

**왜 한 테이블이 아닌가.** 자동저장은 편집 중 계속 일어납니다. Draft 와 Post 가
같은 행이면 독자가 읽는 도중 문장이 바뀌고, "언제 캐시를 깨야 하는가" 라는 질문에
답할 수 없습니다. 발행은 복사이고, 그 시점이 곧 캐시 무효화 시점입니다.

**재발행 시 주소는 유지합니다.** 제목을 바꿔도 slug 는 그대로입니다.
주소가 바뀌면 이미 공유된 링크와 검색 색인이 전부 깨집니다.

## 2. URL 은 `/@handle/slug`

`@` 접두사 덕분에 사용자 블로그 주소가 `/dashboard`, `/settings` 같은 앱 경로와
**구조적으로 충돌하지 않습니다.** Velog 가 `@` 를 쓰는 실질적인 이유입니다.

**구현 주의.** Next.js 는 `app/@folder` 를 병렬 라우트(named slot)로 예약해 두어
`app/@[handle]` 폴더를 만들 수 없습니다. 실제 라우트는 `app/blog/[handle]` 에 두고
`next.config.js` 의 rewrite 로 주소만 `/@handle` 로 맞춥니다.

slug 는 한글을 유지합니다. 로마자로 옮기면 오히려 읽기 어려워집니다.

## 3. 공개 경로는 서버 렌더링, 앱 경로는 클라이언트

|          | 공개 (`/`, `/@handle/...`) | 앱 (`/dashboard`, `/drafts/...`) |
|----------|---------------------------|----------------------------------|
| 렌더링    | 서버 컴포넌트 + 캐시        | 클라이언트                        |
| 인증      | 없음                       | Bearer 토큰                      |
| 백엔드 API| `/api/v1/public/*`         | `/api/v1/*`                      |

**왜 나누는가.** 검색 크롤러와 SNS 미리보기 봇은 로그인도 없고 JS 실행도 기대할 수
없습니다. 공개 글을 클라이언트에서 토큰으로 가져오면 색인이 되지 않습니다.
블로그 플랫폼에서 SEO 는 부가 기능이 아니라 유입 경로 전부입니다.

## 4. 캐시 무효화는 백엔드가 알린다

공개 페이지는 캐시되므로 발행·댓글이 생기면 누군가 캐시를 깨야 합니다.

브라우저가 알리도록 두면 브라우저를 거치지 않는 경로(모바일 앱, CLI, 배치)에서
캐시가 영원히 낡습니다. 그래서 **쓰기를 실제로 수행하는 백엔드가**
`POST {FRONTEND_ORIGIN}/api/revalidate` 로 통지합니다 (공유 시크릿 인증).

- 통지 실패는 본 작업을 실패시키지 않습니다. 시간 기반 재검증이 안전망입니다.
- 통지는 응답 후 백그라운드로 나갑니다. 따라서 **쓰기 직후 읽기에는 짧은 지연**이 있습니다.
- `sitemap.xml` 은 라우트 레벨 `revalidate` 를 두지 않습니다. 그러면 빌드 시점
  (글이 0개일 때) 데이터로 정적 생성되어 굳습니다.

## 5. 소셜 기능과 모더레이션은 같은 시점에 있어야 한다

공개 댓글이 열리는 순간 스팸이 들어옵니다. 그래서 소셜 기능과 함께 넣었습니다.

- **신고**: 같은 사람의 중복 신고는 무시(유니크 제약). 서로 다른 사용자 5건이 쌓이면
  사람이 볼 때까지 **자동으로 가립니다**. 운영자가 없는 시간대에 피해가 쌓이지 않도록.
- **차단**: 차단당한 사람은 그 글에 댓글을 달 수 없습니다.
- **레이트리밋**: Redis 고정 윈도우. Redis 장애 시 통과시킵니다(fail-open) —
  레이트리밋 저장소 때문에 서비스 전체가 멈추는 쪽이 더 나쁩니다.
- **답글은 1단계까지**. 무한 중첩은 모바일에서 읽히지 않습니다.
- **삭제된 댓글은 자리를 남깁니다**. 답글이 달린 댓글을 통째로 지우면 흐름이 끊깁니다.

## 6. 카운터는 비정규화한다

`like_count`, `comment_count`, `follower_count`, `post_count` 를 컬럼으로 둡니다.
목록 정렬에서 매번 `COUNT` 를 도는 것이 가장 먼저 느려지는 지점입니다.
감소 시에는 `CASE` 로 0 아래로 내려가지 않게 막습니다
(`GREATEST()` 는 MariaDB 전용이라 테스트가 도는 SQLite 에서 깨집니다).

## 7. 알려진 한계

- **검색이 `LIKE '%...%'`** 입니다. 인덱스를 타지 않아 글이 늘면 느려집니다.
  MariaDB FULLTEXT 인덱스로 교체해야 합니다.
- **이미지 업로드가 없습니다.** `cover_url` 컬럼만 있고 S3 업로드는 미구현입니다.
- **운영자 화면이 없습니다.** 신고는 쌓이고 자동 가림은 동작하지만,
  검토·해제 UI 는 아직 없습니다 (`ReportRepository.list_open` 은 준비됨).
- **handle 변경 시 기존 글 주소가 전부 바뀝니다.** 경고는 띄우지만 리다이렉트는 없습니다.
- **조회수는 요청마다 UPDATE** 입니다. 트래픽이 늘면 배치·버퍼링이 필요합니다.
